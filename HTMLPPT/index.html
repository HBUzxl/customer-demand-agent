PART 01

理念与规划

为什么做 · 核心判断 · 架构决策 · 规划方法

进入第一部分，理念与规划。

在动手写代码之前，有一个根本性的判断决定了整个项目的走向，那就是：这个系统应该是一个自主 Agent，而不是一条固定流程。

这个判断有多重要？它决定了后面所有的设计——记忆怎么组织、工具怎么暴露、LLM 怎么调用、甚至连前端长什么样。所以我把这块放在最前面讲。

我会先讲项目定位，再讲这个核心理念，然后是技术栈、架构、规划方法（plan tree 和 ADR），最后是记忆系统的三层设计。

what

一句话定位

销售拿到客户的一段话（"网站老被扫""要过等保二级"），交给这个 Agent——它自己判断该查什么、怎么匹配产品、能不能接、还缺什么信息。

输入

客户的原始沟通文本

可能是微信里的一段话、邮件、会议纪要。不要求结构化，Agent 自己理解。

输出

结构化的需求分析

需求理解（业务语言→安全需求）· 匹配产品（+置信度）· 可行性判断 · 待追问信息。

区别于传统工具：不是「固定四步模板」——发一句"你好"它就正常聊天，发真实需求它才调分析工具。判断权在 Agent，不在流程。
这张图要说的就是定位。

左边是输入——销售随手复制过来的一段客户原话，可能是微信里几句、一封邮件、甚至一段会议纪要，不要求任何结构化。

右边是输出——一个结构化的需求分析：需求理解、匹配了哪个产品、可行性判断、还要追问什么信息。

但关键在于底下这句话：它不是「固定四步模板」。你发一句「你好」，它就正常跟你聊天；你发真实需求，它才调分析工具。判断权在 Agent，不在流程。

这是它和传统工具最本质的区别。

core idea

自主 Agent，不是 workflow

❌ 固定 workflow 的问题

把 LLM 锁死成固定步骤，客户描述不同，分析路径本应不同，却被强制走同一模板。

发一句"你好"也给你吐出四步分析模板——用户原话："我发你好，应该正常聊天才对啊"。

✅ 自主循环的样子

调 LLM→ 有 tool_calls?→ 执行工具→ 回填结果↻ 再调
所有能力都是工具调用。LLM 自己挑用什么、什么时候用。强制约束（如"必须给可行性判断"）写在 system prompt，不靠流程。
这页是今天最核心的一页，讲自主 Agent 为什么不是 workflow。

左边的传统做法，是把 LLM 锁死成固定步骤：先需求理解、再产品匹配、再可行性，四步走。问题在哪？客户描述千差万别，分析路径本来就该不同，你硬套一个模板，发句「你好」它也给你吐四步分析。

右边的自主循环是：调 LLM → 看有没有工具调用 → 有就执行、回填结果、再调，直到它给出最终答案。所有能力都是工具调用，LLM 自己挑什么时候用什么。

那些「必须给可行性判断」的强制约束，写在 system prompt 里，而不是靠流程。

这是 ADR-009，后面所有功能都长在它上面。

整体定位就是三个字：轻、可控、核心自己做。

记住一句话：新渠道 = 新 adapter，不动核心，这是可扩展性的根基。

planning

规划方法：plan tree + ADR

docs/plantree/

plan tree —— 规划文档树

注册根（README）→ 每个 plan 独立 README（状态/方案/验证）→ ADR 决策链。17 个 plan，全部记录「为什么做 + 怎么做 + 怎么验证」。

状态流转：Shaping（方案中）→ Ready（可开工）→ Done（落地）。

ADR

12 个架构决策记录

每个决策 = 日期 + 状态 + 决策 + 理由 + 后果。是「为什么这么做」的权威来源，后来者不用重新论证。

例：ADR-009（自主 Agent 非 workflow）、ADR-002（Wiki 不做 RAG）、ADR-008（自研底座）。

讲一下我们怎么管理这个项目的规划和决策。

用的是 plan tree——一个文档树，根是一个注册表，下面每个 plan 一个独立 README，记录「为什么做、怎么做、怎么验证」，状态从 Shaping（方案中）到 Ready（可开工）到 Done（落地）。

另外还有 ADR，就是架构决策记录，每个决策写清楚日期、状态、决策内容、理由、后果。

好处很实在：新同学接手不用猜「当时怎么想的」，直接读 ADR。这也是为什么今天这份 PPT 能做得这么详细——素材都在文档里，我只是把它组织成可讲的形态。

decisions 2/2

ADR-013 ~ 016：自主化重构

ADR-013

业务能力工具化

分析结果是 analysis_submit 工具，不是固定输出格式。Agent 自主判断意图，schema 即契约。否掉「纯 prompt 自主」「意图分类前置」。

ADR-014

统一对话入口

/api/analyze + /api/chat 合并为 POST /api/message，旧入口薄 shim。不做老数据兼容（用户裁决）。

ADR-015

前台/后台域划分

前台（与 Agent 对话）记忆成套全程在线——聊天轮次也要查证/记录；后台（独立任务）无记忆依赖，一次性 LLM 调用。

ADR-016

System Prompt 分层 v2

L0 静态模板 / L1 使用者画像 / L2 会话状态 / L3a 产品目录索引 注入；L3b 其余知识全走工具检索（全量注入已废）。

意义：这四条把「自主 Agent」从口号变成机制——工具化、单入口、域划分、分层注入，共同构成 Agent 的行为契约。
一期之后，我们又做了「Agent 自主化重构」，落下了四条新的决策，编号 013 到 016，它们比前面的十二条更贴近运行时行为。

013 业务能力工具化：分析结果是一个叫 analysis_submit 的工具，不再是硬编码的输出格式。
014 统一入口：原来分开的 analyze 和 chat 两个接口，合并成单一 /api/message。
015 前后台域划分：跟 Agent 对话是前台，记忆系统成套在线；后台独立任务无记忆依赖。
016 prompt 分层：静态模板、用户画像、会话状态、产品索引注入，其余知识全走工具检索。

这四条是「自主 Agent」从口号变成机制的关键。

memory

三层记忆系统

长期记忆

Wiki（文件型）

确定性关键词检索：CJK bigram 分词 + 加权倒排索引（标题权重 3、别名 2.5、标签 2、正文摘要 0.5）。

产品 / 行业 / 用户三层分类，AI 可写但分权限。

短期记忆

Checkpoint 链

结构化状态快照：initial / followup / reanalysis 三种。每轮对话一个 checkpoint。

保留「最近有效分析」回溯——纯聊天轮不会挤掉分析上下文。

历史记录

SQLite 完整轨迹

每条消息、每次工具调用、每个 checkpoint 全持久化。可回放审计。

与短期记忆区分：checkpoint 是工作记忆（内存），history 是持久记录（磁盘）。

记忆系统是分层的，三层各司其职，这页讲清楚。

第一层长期记忆，文件型 Wiki，存「懂的知识」——产品能力、威胁类型、合规要求，确定性关键词检索，中文做了 bigram 分词。

第二层短期记忆，Checkpoint 链，存「当前在想什么」——每轮对话一个结构化快照，保留最近一次有效分析，聊天轮不会挤掉分析上下文。

第三层历史记录，SQLite，存「聊过什么」——每条消息、每次工具调用、每个 checkpoint 全持久化，可回放审计。

一句话记：查证走 Wiki，回溯走 checkpoint，翻旧账走 history。

PART 02

已实现功能

现在能干什么 —— 每项功能的意义

进入第二部分，已实现的功能。这是今天最实的一块。

一共十类功能，每类我都会讲两件事：它是什么、它解决了什么问题。

顺序上，先讲最核心的自主 Agent 循环，然后是统一入口和 Run 任务模型、记忆工具、检索、审核门禁、客户绑定、后台任务、配置观测，最后是会话语义管理和前端体验。

这些功能不是堆砌，它们是层层递进的——先有自主循环，再有统一入口，再有记忆和审核，最后才是体验层的打磨。

feature 01

自主 Agent 循环

核心：analysis_submit 业务工具

寒暄 → 自然语言回复（"你好"就正常聊）

产品概念 → memory_search 查证 + 聊

真实需求 → 调 analysis_submit 提交结构化分析

追问 → 答，或判断需求变化后重分析（is_reanalysis=true）

analysis_submit schema
{
  "demand_analysis": "...",   // 需求理解
  "matched_products": [...],  // 匹配产品+置信度
  "feasibility": "direct",    // 可行性
  "is_reanalysis": false      // 是否重分析
}
意义：摆脱固定四步模板——「你好」不再吐出需求分析 JSON，判断「这是不是真实需求」的权在 Agent。
第一类，也是最核心的——自主 Agent 循环。

核心是一个叫 analysis_submit 的业务工具。Agent 拿到输入后自己判断：
是寒暄？那就自然聊天，不调任何工具；
是产品概念？先 memory_search 查证再答；
是真实客户需求？这才调用 analysis_submit，提交结构化分析；
是追问？答，或者判断需求变了就重分析。

右边的代码块就是分析工具的 schema——需求理解、匹配产品、可行性、是否重分析。

意义就是：摆脱了固定四步模板，「你好」不再吐出需求分析 JSON，判断权还给了 Agent。

feature 02

统一对话入口 + Run 任务模型

一个入口

POST /api/message
{ "text": "客户网站被扫...", "session_id": "..." }

Run 任务模型

202 立即返回，后台 Run 执行——前端不等结果

SSE 订阅流：id: 游标 + x-run: 归属，增量续传

意义：前端即时响应 + 流式体验；刷新页面不丢任务（断点续传），多轮对话各自隔离不串台。
第二类，统一入口加 Run 任务模型。

原来有 analyze 和 chat 两个接口，是 workflow 思维的残留——代码替 Agent 决定了这是分析还是追问。现在合并成一个 POST /api/message。

配合它的是 Run 任务模型：请求进来立刻返回 202 和 run_id，后台去跑 Agent，前端通过 SSE 订阅流来收结果。这样前端不用干等，体验是流式的。

这套东西过了 12 轮审计打磨——事件归属、游标增量、断连恢复、取消、多轮隔离，全是踩坑踩出来的。

意义：刷新页面不丢任务，多轮对话不串台，断连了任务继续跑。

部署还有两点。

一是 Docker：multi-stage 构建，镜像无状态，数据挂卷到 /var/lib/cda，镜像随便重建不丢数据。

二是数据位置三级优先：环境变量 CDA_DATA_DIR 优先，其次 config 的 data_dir，最后 XDG 默认目录。wiki 种子首次启动自动播种；老 ./data 自动迁入新位置、原位保留可回退。

这套设计的目的：部署不丢数据、不脏环境，从开发机到 Docker 到内网都有一致的落盘逻辑。

改数据位置是「只读」配置——涉及迁移，界面不让随便改。
