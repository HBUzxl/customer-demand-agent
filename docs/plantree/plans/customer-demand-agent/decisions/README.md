# 决策记录

## ADR-001：选择 Go 而非 Rust

**日期**：2026-08-13

**状态**：已定

**决策**：使用 Go 作为开发语言。

**理由**：

- 公司技术栈在推 Go，其他师傅用 Go
- 团队协作需要统一语言
- 个人偏好 Rust，但服从团队决策

**后果**：

- Go 的 error handling 模式比 Rust 的 Result 更啰嗦
- Go 缺乏 Rust 的 enum/pattern matching，部分抽象会稍显笨拙
- 但公司内部有成熟的 Go 基础设施

## ADR-002：长期记忆全部由 Wiki 承载，不做 RAG

**日期**：2026-08-13

**状态**：已定

**决策**：全部记忆由 Wiki 层承载——结构化页面 + 关键词检索。不引入向量数据库、embedding、语义相似度检索。

**理由**：

- 产品知识是结构化的，不是非结构化文档
- 知识量小（十条产品线以内），全量注入 context window 可行
- 确定性检索比模糊匹配更适合产品匹配场景
- RAG 需要大量非结构化数据积累才有意义，一期没有这个基础
- 用户明确表示"讨厌 RAG"，一期场景也用不上

**后果**：

- 全部长期记忆走 Wiki，不引入额外存储/检索依赖
- RAG 标记为 Deferred，等非结构化数据积累后再重新评估

## ADR-003：短期记忆采用 Checkpoint 链而非对话缓冲

**日期**：2026-08-13

**状态**：已定

**决策**：短期记忆使用结构化 Checkpoint 链（参考小米 MiMo Code 的记忆架构），不使用对话缓冲 + 滑动窗口 + 压缩摘要。

**理由**：

- 场景不是聊天机器人，而是一次深度分析 + 少量追问
- 追问时需要的是上一次的**分析结论**，不是对话原文
- Checkpoint 链保留结构化状态，每个快照可独立提取
- MiMo Code 已验证：结构化 checkpoint 在长程任务中比压缩摘要更有效

**后果**：

- 三种 checkpoint 类型（initial/followup/reanalysis）
- Prompt 拼装逻辑按操作类型路由
- 引入 notes 机制作为 Agent 唯一临时写入通道

## ADR-004：Wiki 长期记忆分为三层（产品/行业/用户）

**日期**：2026-08-13

**状态**：已定

**决策**：长期记忆的 Wiki 层分为三个子类：

- 产品记忆：产品能力、边界、竞品（确定性最高，标签精确匹配）
- 行业记忆：威胁类型、合规要求、行业痛点（标准字典知识）
- 用户记忆：客户画像 + 使用者画像（实例而非类型）

**理由**：

- 三类记忆的知识结构、检索方式、更新频率不同
- 原"要素记忆"改名"行业记忆"，避免和客户级画像混淆

**后果**：

- Wiki 目录结构变为三层分类
- `LongTermMemory` 接口按记忆类型拆分子方法

## ADR-005：Wiki 支持 AI 自主写入

**日期**：2026-08-13

**状态**：已定

**决策**：Wiki 不是只读的静态知识库。Agent 可以主动调用 `wiki_ensure_page` 创建/更新 Wiki 页面。

**理由**：

- 客户画像是从对话中提取的，人工不可能每次都手动创建
- Agent 发现新威胁模式不应沉默丢失
- 产品记忆仍然以人工审核为主（不能由 AI 说了算）

**后果**：

- `LongTermMemory` 接口暴露写方法
- 行业记忆中 AI 写入的内容打"待审核"标记
- 产品记忆写权限不放给 AI

## ADR-006：前后端分离（Go + React/Vite）

**日期**：2026-08-13

**状态**：已定

**决策**：前后端分离。后端 Go 提供 HTTP/JSON API，前端 React + Vite。

**理由**：

- 待审核机制需要人工审核界面，必须有前端
- 记忆管理（浏览/编辑/删除）也需要 UI，不能靠命令行
- 分析对话页给销售用，是产品形态的一部分
- React + Vite 是公司前端主流栈

**后果**：

- 后端只出 API，不含 HTML 渲染
- 前端四个页面：分析对话、记忆管理、审核队列、设置
- 前后端通过 HTTP/JSON 通信，无共享代码
- 一期后端可先独立跑通（curl 测试），前端后接

## ADR-007：模型管理默认支持 Function Call

**日期**：2026-08-13

**状态**：已定

**决策**：模型管理系统不维护"是否支持 function call"的能力标签。所有模型默认支持 FC。模型管理只管注册/路由/回退/调用封装。

**理由**：

- 主流模型都默认支持 function call，把 FC 当可选能力是过度设计
- 模型数量无所谓，一个 API 可以挂多个模型，也能一个模型打天下
- 路由逻辑因此简化：任务类型 → 模型，不需要考虑 FC 能力匹配

**后果**：

- `ModelConfig` 无 `SupportsFunctionCall` 字段
- 路由表只有"任务类型 → 模型名"一个维度
- 前端配置页只管 endpoint/key/模型列表/fallback 链

## ADR-008：自研轻量 Agent 底座

**日期**：2026-08-13

**状态**：已定

**决策**：不采用 Pi SDK（无 Go 绑定）或其他重型框架。自己先搓一个能跑的粗糙 Agent 底座，再让它自迭代成稳定严谨的版本——目标像 Pi 一样简单但强。

**理由**：

- Pi SDK 是 TypeScript only，且 Pi 是编程 Agent，不适合领域 Agent
- Go 生态无成熟 Agent 框架（langchaingo 不成熟且重）
- 核心循环（调用→工具→回填→再调）不足 500 行，不值得引入框架
- 记忆/模型管理/审核都是自己的核心价值，框架给不了

**后果**：

- 底座 = openai-go（或裸 HTTP）+ 自写循环 + 工具分发
- 先搓粗糙版验证方向，再自迭代稳定化
- 底座与业务解耦：底座是通用 Agent 框架，上层是客户需求分析业务

## ADR-009：顶层是自主 Agent，不是 workflow

**日期**：2026-08-13

**状态**：已定

**决策**：Agent 的顶层结构是自主循环（LLM 自主决定下一步），不是固定 workflow（需求理解→产品匹配→可行性）。所有功能都通过工具调用实现。

**理由**：

- 需求分析不是固定顺序的流水线，客户描述不同，分析路径就该不同
- workflow 把 LLM 锁死成固定步骤，丧失了自主判断力
- 所有能力本质都是工具调用，LLM 自己挑用什么、什么时候用
- 强制约束（如"必须给可行性判断"）写在 system prompt，不需要 workflow

**后果**：

- 循环 = 调 LLM → tool_calls? → 执行工具 → 回填 → 再调，直到最终答案
- workflow 定位：不处处都是。确定性多步流程（如方案生成）包装成工具暴露给 AI
- 工具是唯一能力接口，业务功能也走工具

## ADR-010：历史记录持久化到 SQLite

**日期**：2026-08-13

**状态**：已定

**决策**：完整轨迹（每条消息、每次工具调用、每个 checkpoint）持久化到 SQLite。与短期记忆（checkpoint 链，内存）区分：checkpoint 是工作记忆，history 是持久记录。

**理由**：

- 会话结束后需要能回查——销售问过什么、Agent 怎么答的、为什么这么判断
- 审计需要完整轨迹，不能只有摘要
- 参考 MiMo Code 的 History 层（SQLite 完整轨迹，结构化记忆找不到时回溯）

**后果**：

- 新增存储依赖 SQLite（纯 Go 实现 modernc.org/sqlite）
- 会话列表页 + 会话详情页（回放）
- checkpoint 链仍走内存（工作记忆），history 走磁盘（持久记录）

## ADR-011：多租户隔离（一期只区分，不做权限）

**日期**：2026-08-13

**状态**：已定

**决策**：引入 tenant_id 做多租户区分。一期只做数据隔离，不做权限（无 RBAC）。

**理由**：

- 多个销售共用一套系统，各自的会话和历史要隔开

**后果**：

- tenant_id 贯穿：会话、历史记录、使用者画像
- 共享范围：产品记忆、行业记忆、客户画像（组织级知识，不隔离）
- 隔离范围：session、history、使用者画像（个人级数据）
- 账户：每个使用者一个 tenant，登录/标识方式后续定

## ADR-012：消息入口抽象，为钉钉留口子

**日期**：2026-08-13

**状态**：已定

**决策**：Agent 核心不直接跟 HTTP 或钉钉耦合。引入 Channel（消息入口）抽象：HTTP 是一期的实现，钉钉 webhook 是未来的第二个实现。未来确定对接钉钉。

**理由**：

- 钉钉机器人通过 webhook 推送消息、需要主动推送回复，协议与 HTTP/JSON 不同
- 如果 agent 核心直接绑 HTTP，未来对接钉钉要改核心
- Channel 抽象让"新接入一个渠道"只是新增一个 adapter，不动核心

**后果**：

- 核心只处理归一化的 InboundMessage / OutboundMessage
- Channel 负责：传输（HTTP/钉钉 webhook）+ 格式适配（钉钉消息格式 ↔ 内部格式）
- 一期只实现 HTTP Channel，钉钉 Channel 留接口待未来实现
- 钉钉对接排在 Deferred，但架构上已经预留
