# 决策记录

## ADR-013：业务能力工具化——分析结果通过 `analysis_submit` 工具提交

**日期**：2026-08-14（规划）

**状态**：已落地（2026-08-14）

**决策**：需求分析、可行性判定不再是固定的输出格式，而是一个 Agent 工具
`analysis_submit`。Agent 自主判断输入意图：是真实客户需求时，先自主检索记忆、
思考，然后调用 `analysis_submit` 提交结构化结果；是寒暄/闲聊/简单问题时，直接
自然语言回答，不调用该工具。最终答案（done）始终是自然语言文本；结构化分析
作为工具调用的产物挂在消息上。

**理由**：

- 现状「强制 jsonOutput + prompt 框死分析 JSON」把 Agent 退化成了单步分析函数
  ——任何输入都硬套分析模板（发"你好"回说明书），违背 ADR-009 的自主性
- 工具化后，"要不要做分析"由 LLM 判断，"分析结果长什么样"由工具 schema 约束
  （比 prompt 里贴 JSON 模板更可靠，schema 即契约）
- 对流式友好：用户先看到 Agent 的自然语言思考/说明（content 流），结构化卡片
  在工具调用发生时即时出现，不需要等最终 JSON 拼完

**被否方案**：

- *纯 prompt 自主*（不加工具，让 LLM 自己决定输出 JSON 还是自然语言，后端探测
  解析）：输出格式歧义大，解析器要猜"这是聊天还是分析"，前端渲染分支脆弱。
  工具调用是显式信号，无歧义。
- *意图分类前置*（先调一次 LLM 分类"聊天/分析"再路由）：两次调用延迟翻倍，
  且分类错了整个会话方向就错；不如让同一个循环自主决策。

**后果**：

- 新增 agent 层业务工具注册（区别于 memory 工具），工具结果进入 Trace 与 history
- `runStreaming` 不再强制 jsonOutput；`parseAnalysis` 的文本兜底逻辑删除
- done 事件语义变化：`content`（自然语言答案）总是有；`analysis` 仅当
  analysis_submit 被调用过
- 前端以 `analysis` 是否存在决定是否渲染 ResultCard，文本部分始终渲染 markdown

## ADR-015：对话域划分——前台（完整记忆系统）/ 后台（无记忆依赖）

**日期**：2026-08-14（用户裁决）

**状态**：已落地（2026-08-14）

**决策**：对话域划分为前台与后台两类：

- **前台**（与 Agent 的对话，`/api/message` 主链路）：**对话是和 Agent 的对话，不是普通 chat 形式——所有轮次（含聊天/寒暄）Agent 的记忆工具全程在线且应被自然使用**：
  - 聊天中涉及产品/威胁/合规事实 → `memory_search` 查证后回答（不凭记忆瞎说）
  - 聊天中出现新客户信息/线索 → `memory_observe` / `memory_ensure` 记录
  - 真实客户需求 → 完整分析 + `analysis_submit`（唯一保留的"分析专用"工具）
  - Checkpoint 链覆盖全轮次（含纯聊天轮次的轻量 checkpoint）、长期 Wiki 记忆、
    assembler 拼装、history 持久化、断点续传——记忆系统成套，不可裁剪
- **后台**（预留的独立任务，如摘要/压缩/批量处理，`TaskBackground` 路由）：**无
  记忆系统依赖**——不建 checkpoint、不注入记忆上下文，纯一次性 LLM 调用。
  一期不实现后台任务，只在模型路由（TaskType）与架构分层上留好口子。

**理由**：记忆系统是前台体验的核心（上下文连续性、客户画像积累、断点续传），
必须成套不可裁剪；后台任务是独立的功能性调用，套上记忆系统只会增加复杂度与
token 成本，没有收益。

**后果**：

- agent 层的 checkpoint 创建对**所有前台轮次**生效（含纯聊天），不再只在分析
  轮次创建
- **prompt 明确指引：聊天轮次也要用记忆工具**（查证/记录），不是裸 LLM 对话
- assembler/记忆注入只挂在前台链路；后台任务直连 model.Manager 不经过 agent
  记忆循环
- TaskBackground 路由保留但一期无调用方（ADR-007 已有该枚举）

## ADR-014：统一对话入口 `/api/message`，旧入口做兼容 shim

**日期**：2026-08-14（规划）

**状态**：已落地（2026-08-14）

**决策**：`/api/analyze` 与 `/api/chat` 合并为单一 `POST /api/message`
（body: `{text, session_id?}`）。后端不再区分"分析/追问"两种模式——同一个自主
循环处理所有输入。旧的两个端点保留为薄 shim（内部转发到统一逻辑），前端切换
后择期删除。

**理由**：

- 双入口是 workflow 思维的残留：代码替 Agent 决定了"这是分析还是追问"
- DetermineOp 仍保留，但用途收窄为**checkpoint 语义判定**（新文档→initial、
  同文档追问→followup、换文档→reanalysis），不再决定输出格式与 prompt 分支
- 前端 `send(text, kind)` 的 kind 分支可删，SSE 消费逻辑统一

**后果**：

- e2e/集成测试的端点与断言更新
- **不做老数据兼容（用户裁决）**：老数据会被处理去适配新系统；reconstruct 一律按
  新契约（content 自然语言 + tool_calls.message_id 归属）
- 钉钉 Channel（未来）只需要对接一个入口
