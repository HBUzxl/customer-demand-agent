# APISEC 上线运营指南

# 上线配置

## 第一步：根据已知标准配置基础配置

### 源 IP 配置

由于客户网络流量复杂，可能经过多个代理网关后，TCP 层源 IP 已经无法代表原始发起请求的人 / 客户端，此时可以根据请求头中字段进行获取。

可以在 资产梳理 / 其他配置 / 基础流程配置 中配置源 IP 获取方式，获取过程中将依次尝试，支持从 X-Forwarded-For 中获去，支持从自定义 Header 中获取，多条配置时顺序可拖动。

![image.png](images/APISEC上线运营指南/61d1218a-30d6-4b47-babf-9ed69954bc44.png)

### IP组配置

为实现对流量来源与目标的区域划分，需要根据已知的、有需求的 IP段 进行划分，如非常见的内网 IP 网段（公网私用），或部门、子公司间流量。

可以在 资产梳理 / 其他配置 / IP组 中进行配置，内置一个 IP组 包含常规内网 IP 网段。

![image.png](images/APISEC上线运营指南/4d3731b6-43cf-414c-8e38-edfef5cad75a.png)

### 流量筛选配置

由于流量镜像的特点，可能接收到 “内网到内网”，“内网到外网”，“外网到内网”，多种不同方向的流量，一般我们需要过滤掉一些不重要的流量，比如上班摸鱼看 iqiyi 的流量。

可以在 资产梳理 / 其他配置 / 流量匹配名单 中进行配置。

![image.png](images/APISEC上线运营指南/c60076a2-d34a-472c-ae94-5e5a77ae4c2e.png)

规则会从上到下按顺序执行，命中条件则执行动作并不再继续匹配。兜底为全部流量识别，即如果想只识别某部分流量，需要配置一条动作为 “不识别” 的规则。

### 应用管理（站点分类）

在 应用管理 中，支持将某些域名下的子域名直接移入一个特定应用，这个在客户有重点关注或者站点分类需求时，且前期知道范围的情况下，可以预先做配置。

![image.png](images/APISEC上线运营指南/ba416cba-dca3-4a11-9ec3-16b8e3219040.png)

内置一个默认应用，在没有应用被匹配到时，站点将被归类到 默认应用。

![image.png](images/APISEC上线运营指南/77979ef6-a5af-4c0b-9797-f486dbb4a088.png)

站点可以被移除应用，当站点不在任何应用下时，将不会再处理对应站点的流量。

![image.png](images/APISEC上线运营指南/085174c0-05f9-4f74-a6a0-5619f482cdc5.png)

默认应用可以不存在，即可以通过应用配置达到只匹配默写域名及其子域名的效果。

### 初步配置身份信息标识、业务成功标识

**这两个配置非常重要，会直接影响风险检测中与用户、请求成功相关的策略的检测结果。**

**身份信息标识**用于标识每个请求是有哪个用户触发的，它可能是一个 user id，也可能是一个 session id。一些常见的 key 已经被内置到系统，如 sessionid、PHPSESID 等。

大多数客户内部都会有一些统一的、不常见的 key 作为身份鉴权的标识，比如 icbc\_token 这种带有明显客户特征的字段，这些字段可能是 Header 也可能在 Cookie 中。但是这些字段在对客户部署前无法提前预知，需要和客户沟通收集，或者通过观察 waf 等流量设备的流量日志来猜测哪些是客户系统中使用的身份信息标识。

可以在 资产梳理 / 资产发现配置 / 身份信息标识 中进行增加。

![image.png](images/APISEC上线运营指南/d63fefc8-edf2-4354-8fa7-421e511406c6.png)

**业务成功标识**用于标识每个请求是否成功。如在未鉴权检测中，对于没有身份标识的请求，如果业务请求成功则表示对应 API 存在风险，如果不成功则应当忽略（比如未登陆时访问失败会自动跳转，那么这个请求应表示不存在未鉴权风险）

一般系统使用响应码表示，但现代很多框架中，业务失败的响应码也会为 200 但是会在响应体中额外增加一个 code 字段（或其他字段）来表示业务执行是否成功，同时不同系统表示成功的 code 也不尽相同（有 0、200、100 等等）。

系统内置了一些常见的判断逻辑，但仍可根据客户已知情况进行丰富。

可以在 资产梳理 / 资产发现配置 / 业务成功标识 中进行增加。

![image.png](images/APISEC上线运营指南/0339c836-078c-4a03-be89-d8d9e2fe635d.png)

在 数据安全 / 数据分类分级 中可以配置数据分类层级，并将数据分类与数据标签进行关联，同时配置分级属性。

#### API 结构

**API 结构**表示 API 在调用、解析结果时用到的数据结构，其中包含 Query、Body 中传递的数据，也包含 Header 中传递的一些自定义值（如 sessionid 等鉴权信息，设备信息）

当以 HOST Urlpath Method 作为基础的 API 区分条件时，在现代的 API 实现逻辑中，可能会存在多种不同的结构但数量一定不会很多，当结构存在 5 个时，那么可能是需要进行**谓词拆分**的。

API 的结构解析支持深度解码技术，不需要手动配置即可自适应编码逻辑，识别实际传输的字段。为了能够清晰的表达 解码路径、参数名、参数结构，API 结构的参数名存在特殊的定义方式，具体逻辑如下：

1.  以 . 进行分割，形成的列表中每一位表示一个新的层级或解码过程，如 {"a": {"b": 1}} 将表示为存在一个参数 a.b 参数类型为 number
    
2.  如果遇到由尖括号包裹起来的内容（如<GZIP> <BASE64> <JSON> 等），表示该位置值经过了相应的解码方式进行解码，如 <GZIP>.<BASE64>.<JSON>.a.b 则表示 {"a": {"b": 1}} 这样的结构经过了 json 编码后，由经过 base64 编码，最后经过 gzip 压缩才放在相应的报文中
    
3.  $array 表示存在一层数组结构，$array的下一层是数组中一个元素的字段，如 <JSON>.data.$array.user.id 表示 {"data": \[{"user": {"id": 1}}\]}
    
4.  HTML 页面较大较复杂，且结构化解析的结果并没有什么实际价值，故不会执行 HTML 解码过程
    

一些例子：

| <JSON>.code | {<br>    "code": 0,<br>    "data": {<br>        "orders": \[<br>            {<br>                "id": 1,<br>                "remark": "2024年第一单",<br>                "total": 1500000<br>            },<br>            {<br>                "id": 2,<br>                "total": 1500000<br>            },<br>            {<br>                "id": 3,<br>                "remark": "重点客户 X",<br>                "total": 1500000<br>            }<br>        \],<br>        "username": "John"<br>    }<br>} |
| --- | --- |
| <JSON>.data.username |
| <JSON>.data.orders.$array.id |
| <JSON>.data.orders.$array.remark |
| <JSON>.data.orders.$array.total |

| <BASE64>.<QUERY>.name | bmFtZT1Kb2huJmNvZGU9MTAwJnRpbWVzdGFtcD0xNzI1NTA3MjE5<br>注：base64 解码后为<br>name=John&code=100&timestamp=1725507219 |
| --- | --- |
| <BASE64>.<QUERY>.code |
| <BASE64>.<QUERY>.timestamp |

| Authorization.<JWT>.sub | 参数位置为 Header，表示 Authoization Header 的值为：<br>eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4iLCJpYXQiOjE1MTYyMzkwMjJ9.A6Ak1IC1KhtSzAor4-i-bZhmCHQya-sRlPy9-DGgQwA |
| --- | --- |
| Authorization.<JWT>.name |
| Authorization.<JWT>.iat |

### API 资产发现配置

API 资产发现后，需要对识别到的资产进行一定的确认与检查，确认 API 资产的准确性与 API 资产相关配置足够准确能够用于风险检测。

#### Restful 聚合规则

Restful 规范除了 Method 表达执行动作，同时也表示 Url 用于标识 “资源”，如数据库中的每一个用户的信息，每一个订单的信息，都是 “资源”。当需要表示某一个资源时，则需要有具体的 id 进行表示，所以一般参考 Restful 规范的 API 在 Url 中存在表示 id 的部分，如 /project/1/order/2/info 表示 “项目 id 为 1 的项目中，id 为 2 的订单的信息” 这样的一个资源。

产品内置基于 Restful 规范的自动聚合逻辑，将 /project/1/order/2/info，/project/1/order/5/info，/project/2/order/12/info 等一系列的 Url 聚合为同一个 API Url：/project/{:num}/order/{:num}/info。

在 资产梳理 / 资产发现配置 / Restful 聚合规则 中可以查看、配置 Restful 的聚合规则。

![image.png](images/APISEC上线运营指南/143dd996-c21e-4de7-bd16-040821745b99.png)

聚合规则的详情中展示相关规则涉及到的 API 资产，可以辅助确认该规则是否合理。

![image.png](images/APISEC上线运营指南/56ea92c5-f7ff-4cec-b89d-7db287db4f7c.png)

当发现不合适的聚合结果时，可以删除聚合规则并增加“不聚合”规则来阻止自动聚合逻辑。发现未自动发现的聚合路径时也可以手动增加聚合规则。

![image.png](images/APISEC上线运营指南/48d5f0e0-246f-4efe-9066-6d263fac6bfe.png)

#### 谓词拆分规则

现代一些系统或规范（如 Json-RPC）中，对于不同的 API，他们有相同的 Host、Url、Method，但是会根据 Query 或 Body 中的某个字段执行不同的 API。

在 **API结构** 中提到，每个 API 资产会对请求数据的结构进行解析，并根据每次请求的数据结构的相似性识别出来多种数据结构。当前请求数据结构足够多时，可以推断其中可能存在一个 “谓词” 用于标识该 Url Method 下的不同动作，即不同 API。

![image.png](images/APISEC上线运营指南/905a0de4-7f51-430e-9bfd-bae73ecf2575.png)

在 资产梳理 / 资产发现配置 / 谓词拆分规则 中可以看到系统自动发现的 “谓词” 字段。用户可以在与业务实际确认后，开启对应的谓词拆分规则。

![image.png](images/APISEC上线运营指南/3856749a-cfa4-400b-b7b2-c1cd736fb200.png)

规则启用后，后续的流量会命中该规则，并拆分为多个 API 资产。井号 # 后面的部分表示 “谓词” 字段的不同值。

![image.png](images/APISEC上线运营指南/3b7bdeab-9c81-416e-bf2c-b9cdd595b0da.png)

#### 身份标识

在第一步中配置的身份标识规则是对流量进行身份标识发现的基础规则，即 “如果流量中有这些字段，那么他们会代表这个请求的身份信息”。

而当 API 资产被发现以后，API 资产的流量中被识别出来的身份标识字段，将被认为是这个 API 可能的身份标识字段。这会产生三种结果：

1.  发现有且仅有一个身份标识：这意味着这个 API 大概率是以此进行身份识别的，可以直接进行确认
    
2.  发现多个身份标识：这意味着这个 API 的客户端访问过程中可能会经历多个身份验证机制，或包含其他业务跳转导致的字段冗余，目前需要客户确认其中之一，哪一个是实际有效的
    
3.  未发现身份标识：这有三种可能
    
    1.  首先该 API 可能不需要鉴权信息，如一些首页页面
        
    2.  其次该 API 的鉴权信息可能是特殊的字段，系统未能发现，需要用户手动录入
        
    3.  最后该 API 可能是未鉴权 API，返回业务信息，且请求过程不包含身份信息，也不对身份信息进行验证
        

在 资产梳理 / 资产发现配置 / 身份标识 / 标识确认 中，可以对身份标识进行批量确认，一般一个站点会使用相同的身份标识，建议优先确认 站点 级别的身份标识，这样也可以减少系统内需要推送的规则数量的数量级。

![image.png](images/APISEC上线运营指南/a52a1402-d8eb-43d4-9e8a-92cd93327ed7.png)

另外在站点详情中也可以直接对该站点的身份标识进行编辑与确认。

![image.png](images/APISEC上线运营指南/c26ccfc1-7b5d-4b3a-b662-2ba5c48dfb4f.png)

#### 业务成功标识

#### 可编程解析

在一些特殊的系统中，URL 存在特殊的逻辑，如下图所示，URL 中包含 “谓词” 来表示实际的 API 动作，同时还包含相应的数据传输，由于传输的数据不断变化，所以 URL 也将随之变化，导致根据 URL 识别的 URL 资产数量将膨胀得非常庞大，无论是根据 URL 记录还是将 URL 聚合，都是相当不准确的 API 资产记录。

![image.png](images/APISEC上线运营指南/74faf9f2-52a4-4ef6-9476-677220b275c1.png)

可编程解析功能通过 Lua 脚本将这些无法常规处理的 URL、Body 等内容，通过定制化的脚本进行解析，并可将解析出的数据覆盖到前序解析出的 API 资产数据中，一方面将 API 资产梳理清晰，优化数据结构解析，另一方面为后续敏感数据识别提供更多数据基础。

![image.png](images/APISEC上线运营指南/4613a7be-0b74-4660-9f45-45408692ac80.png)

在 资产梳理 / 资产发现配置 / 可编程解析 中，可以开启或创建相应的解析脚本。

![image.png](images/APISEC上线运营指南/c93d1534-8c10-4faf-8920-c69f18817263.png)

#### 1 对 1 资源位配置

在 API 的数据交互过程中，数据的字段代表了一种交互的资源类型，而值则表示了交互的资源。如 GET /order?id=1 时表示获取 订单 这种资源，并且获取 id 为 1 的资源。

结合每一次获取资源的请求中的 用户身份信息，可以梳理出来哪些资源是被某些用户所独享的，即1对1资源。1对1资源位则表示在这些 API 中，哪些字段是表示了这种 1对1资源 的字段。

在 资产梳理 / 资产发现配置 / 1对1资源位 中，可以配置 1对1资源位是否开启。

![image.png](images/APISEC上线运营指南/abbd22e8-0e8e-4d0d-8bbb-c221380e793f.png)

开启 1对1 资源前需要先开启 K-V记录配置，将请求的 K-V 数据记录后才可以自动梳理 1对1资源位。

**由于 1对1资源位 计算非常消耗资源，建议只针对固定的重要 API 进行开启。**

**由于 K-V 记录会随着请求的复杂程度成倍上涨，远超原本 QPS 与 IO 带来的 iops，所以默认关闭，建议针对需要处理的 站点、API 进行配置。**

#### 策略创建与编辑

不同策略的配置内容不完全相同，如弱密码需要配置要检测的字段名特征，频率监测策略需要选择通过阈值检测还是基线检测等。

发现策略基本都有的配置项：

*   任务状态：即是否启用
    
*   策略名称
    
*   备注
    
*   生效范围：一方面由于部分策略性能消耗比较大，希望可以限制策略运行的范围，只在需要关注的 API 或站点上运行；另一方面通过对范围的配置可以简单的实现一些场景化策略，如选择登陆接口的 IP 访问频率监测策略，可以模拟撞库、暴力破解策略
    
*   自动确认风险状态：是否自动将发生的风险确认为脆弱性，在后续脆弱性部分将进行详细说明。
    

![image.png](images/APISEC上线运营指南/27ca4ee8-0b1e-430f-bd1e-886d45baf135.png)

### 风险策略的开启建议

产品默认每个策略带有一个未启用的策略。没有直接开启主要是考虑性能影响无法准确估计，不希望在无人日常关注情况下全量运行。

如下类型策略检测逻辑较为简单，可在配置完成后开启：

*   使用弱密码获取权限
    
*   使用不常见的 HTTP 方法
    
*   请求无鉴权信息
    
*   非工作时间访问
    
*   监测全站请求频率
    
*   监测站点请求频率
    
*   监测 API 请求频率
    
*   IP 访问频率异常
    
*   URL 包含鉴权信息
    
*   响应内容长度异常
    
*   SSRF 攻击
    
*   注入攻击
    
*   IP 访问敏感数据频率异常
    
*   返回信息含有密码项
    
*   单次传输过多敏感数据类型
    
*   包含过度的错误提示
    
*   不安全的配置
    
*   访问敏感信息时未鉴权
    
*   请求内容长度异常
    
*   包含不必要的服务器信息
    
*   用户访问频率异常
    
*   用户访问敏感数据频率异常
    
    以下类型策略对于性能消耗较大，和 IP、用户数量等正相关，建议逐个开启并观察一天以上的时间后，再根据资源开启后续的策略：
    
*   相同 IP 使用不同身份标识
    
*   相同 Session 多来源请求
    
*   用户名使用频率异常
    
*   来自新 IP 段的访问
    
*   账号被多省份 IP 使用
    
*   扫描器 IP 访问
    

以下类型策略需要结合实际业务情况（如用户的系统是否一般只被固定地区的设备访问，例如分子公司的固定机房），与用户内部的合规要求，进行较精细的策略配置工作来减少误报：

*   API 从未使用鉴权信息
    
*   设备访问频率异常
    
*   监测应用请求频率
    
*   监测广域网 IP 访问
    
*   监测指定 IP 访问
    
*   监测访问者省份范围
    
*   监测访问者国家和地区范围
    
*   请求低频的权限类 API
    
*   群控与网关访问
    
*   来自新 User-Agent 的访问
    
*   监测指定 User-Agent 访问
    
*   利用供应商 API 漏洞的攻击
    

“利用资源 ID 进行水平越权” 策略较为特殊，需要相当大的资源，需要提前开启 1对1资源位 的识别功能，建议对重要的 API 逐个开启。

# 长期运营

## 运营思路

由于 API安全 尚处于一个开始阶段，许多客户或有一种 “我该怎么做” “这么做是不是可以了” 等等的想法，但实际上并没有那么复杂，比起常规的 waf 日志分析，需要更进一步了解下 “业务情况” —— 无论是通过产品功能还是通过和业务部门交流 —— 对一些列请求构成的事件进行分析。

从产品使用的角度上来讲，需要持续的关注几个方面：

1.  资产梳理
    
2.  敏感数据趋势
    
3.  风险检测结果
    

并在发现问题时，可以初步在产品中进行一些信息获取与分析，如通过访问的上下文判断是否合理，通过溯源分析判断数据泄露的形势等等。

### 联动处置

APISEC 结合雷池 Waf 可以在 APISEC 的风险策略检测出风险事件后，根据已配置的规则模版，向已配置的联动设备下发自定义规则，实现对风险事件的自动化检测与阻断。

![image.png](images/APISEC上线运营指南/a0b55c21-2cd6-4213-b2ac-0741b8c37009.png)

#### 配置过程

1.  在 waf 创建 OpenAPI token
    
    ![image.png](images/APISEC上线运营指南/85a7dfb7-36ae-4798-92b9-6bb7fa4af2a7.png)
    
2.  在 APISEC 中创建对应的联动设备，注意设备地址要包含协议与端口，如 https://10.2.2.1:9443
    
    ![image.png](images/APISEC上线运营指南/a73d12d1-aee9-468e-869c-4b1a726467f3.png)
    
3.  创建后，将持续通过心跳探测联动设备是否存在且有足够权限可访问
    
    ![image.png](images/APISEC上线运营指南/deb84c3c-7247-4ecc-88ca-8f6a81eb9ef3.png)
    
4.  在风险策略详情中增加新的联动规则模版，当有相关风险事件触发时，将自动根据风险事件模版创建联动规则，并下发到联动设备
    

![image.png](images/APISEC上线运营指南/062e8055-1b6c-4ef4-8ff8-57b37e87c5d1.png)

![image.png](images/APISEC上线运营指南/8f0d4da1-9ce7-4ca8-a67b-337a576b444e.png)

规则模版支持的匹配条件与雷池 waf 相同。

同时支持如下通配符内容用于匹配每个事件中的实际值：

*   {{$method}} http 请求方法
    
*   {{$host}} 域名（如非80，443时包含端口）
    
*   {{$urlpath}} urlpath
    
*   {{$src\_ip}} 源 IP
