# 雷池 SafeLine 3.0 软件安装部署手册

## 1 部署前准备

### 1.1 安装部署手册说明

**在执行实际部署前，需要提前进行安装环境检查与设置。**

### 1.2 安装说明

#### 1.2.1 名词定义

##### 1.2.1.1 节点

- 指一台服务器，可以是物理服务器、云服务器

- 一套软件版部署可以包括多个节点，在管理界面的「状态监控-设备运行状态」可以查看各个节点状态

- 节点的数量由 License 进行限制，管理节点、检测节点无异，都包括在节点限制中

##### 1.2.1.2 安装目录

- 指雷池资源主要保存目录，默认值为 /data/safeline

##### 1.2.1.3 数据盘

- 指安装目录所在的硬盘（此概念一般出现在硬件 WAF 中）

#### 1.2.2 常用工具列表

Linux 下常用工具列表，可以参考进行安装：

##### 1.2.2.1 工具说明

tcpdump：网络抓包工具

curl：HTTP 请求工具

vim：编辑文件工具

strace：跟踪系统调用工具

tmux：终端窗口工具

net-tools：其他网络工具

sysstat：性能监控

##### 1.2.2.2 工具安装命令

Ubuntu：`apt install -y tcpdump curl vim strace net-tools sysstat`

CentOS：`yum install -y tcpdump curl vim strace net-tools sysstat`

### 1.3 安装前准备

以下操作需在 root 权限下执行

**步骤 1**：将安装包拷贝到待安装节点。安装文件通常命名为 `safeline-3-software-installer-*.bin`；定制版本或 ARM 版本的文件名可能不同，但安装方式基本一致。安装包文件名通常包含 MD5 校验值，可执行 `md5sum safeline-3-software-installer-*.bin` 核对校验值

**步骤 2**：执行安装包加载。由于执行安装包会自解压安装包内容，所以建议将安装包放入一个单独的文件夹运行：

   - 创建安装目录：`mkdir -p /data/safeline`
   - 将安装包移动到临时目录并重命名：`mv safeline-3-software-installer-*.bin /data/safeline/safeline-3-software-installer.bin`
   - 进入临时目录：`cd /data/safeline`
   - 赋予执行权限：`chmod +x safeline-3-software-installer.bin`
   - 运行安装程序：`./safeline-3-software-installer.bin -p 安装包密码`

如果执行过程中，安装程序提示是否升级引擎，则默认回车为进行引擎升级（推荐操作）

**步骤 3**：校准操作系统时间。使用 `date` 命令查看操作系统时间，如果时间不正确，可以通过以下两种方式修改：

- 方案一：无法访问公网但内网有 NTP Server 时，由客户提供 NTP Server 地址，在 WAF 中配置自动同步时间

- 方案二：客户没有 NTP Server 且无法访问公网时，执行 `timedatectl set-time '2025-11-20 16:10:40'` 手动修改时间

**步骤 4**：执行安装前检查。运行 `minion check run before-install` 查看检查结果，所有 Failed 项目都需要修复后才能继续安装

**步骤 5**：如果 Failed 项中出现 `system do not support ipv6`，必须停止安装并执行 `reboot` 重启系统。系统启动后，再次执行 `minion check run before-install`，确认该 Failed 项已消失后再继续安装

## 2 软件部署

### 2.1 软件单机部署

**确保已完成部署前准备中的所有操作，否则会导致安装失败**

**步骤 1**：初始化部署模式：`minion setup -p /data/safeline -t Software --node-type Single`

**步骤 2**：启动基础平台服务：`systemctl start minion`

**步骤 3**：输入 `docker ps` 检查 WAF 各服务启动状态，当所有服务的 status 值都为 up，并且没有 unhealthy 出现时，证明安装成功

**步骤 4**：浏览器打开 `https://<当前机器 IP>:9443`，上传产品证书。登录后进入「状态监控 > 设备运行状态」，确认部署节点状态正常

### 2.3 软件复杂集群部署

复杂集群将管理、日志处理和流量检测/转发拆分到不同节点，适合日志量较大或需要独立扩展日志处理能力的场景。单管理复杂集群至少包含 1 个无日志管理节点、1 个日志节点和 1 个工作节点；生产环境使用 etcd 服务发现时，建议部署 3 个或以上奇数个日志节点。

复杂集群仅支持软件部署类型。使用前可执行 `minion setup --help`，确认安装包的可用节点类型中包含 `ManagementWithoutLogging` 和 `Logging`。

#### 2.3.1 部署规划

本文使用以下五节点环境说明安装过程。外部 IP 用于管理访问和静态模式；日志节点内部 IP 用于 etcd 集群、服务发现和日志服务广播。为避免泄露实际网络信息，正文和截图均使用尖括号形式的脱敏占位符；执行命令前必须将占位符替换为实际 IP。

| 节点角色 | 外部 IP | 内部 IP | 节点类型 |
| --- | --- | --- | --- |
| 管理节点 | `<MANAGEMENT_IP>` | `<MANAGEMENT_INTERNAL_IP>` | `ManagementWithoutLogging` |
| 日志节点 1 | `<LOGGING_1_IP>` | `<LOGGING_1_INTERNAL_IP>` | `Logging` |
| 日志节点 2 | `<LOGGING_2_IP>` | `<LOGGING_2_INTERNAL_IP>` | `Logging` |
| 日志节点 3 | `<LOGGING_3_IP>` | `<LOGGING_3_INTERNAL_IP>` | `Logging` |
| 工作节点 | `<WORKER_IP>` | `<WORKER_INTERNAL_IP>` | `Worker` |

部署前须确保各节点时间同步，并按所选模式放通以下端口。etcd 的 `2379`、`2380` 端口应仅在可信内部网络中开放，不应暴露到公网。

| 访问方向 | 端口 | 用途 |
| --- | --- | --- |
| 日志节点、工作节点 → 管理节点 | `9443/TCP` | 节点注册及管理通信 |
| 日志节点 → 管理节点 | `5432/TCP`、`6379/TCP`、`9000/TCP`、`3336/TCP` | PostgreSQL、Redis、ClickHouse、WAAP |
| 工作节点 → 日志节点 | `3334/TCP` | 向 mario-aggregator 发送日志；两种模式均需要 |
| 日志节点、工作节点 → 日志节点 | `2379/TCP` | etcd 客户端访问，仅 etcd 模式需要 |
| 日志节点 ↔ 日志节点 | `2380/TCP` | etcd 成员通信，仅 etcd 模式需要 |
| 日志节点 ↔ 日志节点 | `3335/TCP` | mario 服务发现后的日志转发，仅 etcd 模式需要 |

每台机器均需先完成 1.3 节的安装包加载、时间校准和安装前检查。可使用 `timedatectl status` 或 `chronyc tracking` 检查时间同步状态；节点时钟明显不一致时禁止启动 etcd 集群。

#### 2.3.2 部署无日志管理节点

静态和 etcd 模式共用同一个管理节点。

**步骤 1**：在管理节点初始化无日志管理模式：

```bash
minion setup -p /data/safeline -t Software --node-type ManagementWithoutLogging
```

初始化完成后，妥善保存命令输出的 `Database Password`、`Minion API Token`、`Bot Js Module Location` 和 `Minion Cert`。这些内容包含敏感信息，后续配置日志节点和工作节点时使用，不要写入文档、截图或普通日志。

**步骤 2**：启动基础平台服务：

```bash
systemctl start minion
```

**步骤 3**：执行 `docker ps`，确认 `mgt-api`、`mgt-postgres`、`mgt-redis`、`mgt-clickhouse`、`waap` 等管理服务已经启动。无日志管理节点不运行 `mario`、`mario-aggregator` 或 `mario-collector`。

**步骤 4**：浏览器打开 `https://<MANAGEMENT_IP>:9443`，上传产品证书并确认可以登录。

如果需要管理节点 HA，可分别使用 `ManagementPrimaryWithoutLogging` 和 `ManagementStandbyWithoutLogging`，其 VIP、SLB、PostgreSQL 主备等配置方法与 2.4 节一致。日志节点的 `Management service host or IP` 必须能够访问当前主管理节点的 `5432`、`6379`、`9000` 和 `3336` 端口；只代理 `9443` 的 SLB 地址不能用于该字段。

#### 2.3.3 静态地址模式

静态模式不依赖 etcd。每个工作节点直接配置全部日志节点地址，安装程序会自动为地址追加 mario-aggregator 端口 `3334`。

**步骤 1**：分别在三个日志节点执行：

```bash
minion setup -p /data/safeline -t Software --node-type Logging
```

按照提示填写以下信息：

| 配置项 | 本文示例或填写说明 |
| --- | --- |
| `Database Password` | 管理节点初始化时生成的数据库密码 |
| `Minion API Token` | 管理节点初始化时生成的 API Token |
| `Location of Bot Module` | 管理节点初始化时输出的 Bot 模块位置 |
| `Management Address with Port and Protocol` | `https://<MANAGEMENT_IP>:9443` |
| `Minion Cert` | 管理节点初始化时生成的完整证书内容 |
| `Management service host or IP` | `<MANAGEMENT_IP>`，只填写实际主机名或 IP，不填写端口 |

**步骤 2**：每个日志节点配置完成后执行 `systemctl start minion`。使用 `docker ps` 确认 `mario` 和 `mario-aggregator` 已启动，且状态中没有 `unhealthy`。

**步骤 3**：在工作节点初始化 `Worker` 模式：

```bash
minion setup -p /data/safeline -t Software --node-type Worker
```

按提示填写管理节点生成的连接信息。出现 `Logging node hosts or IPs (comma-separated)` 时，输入工作节点实际可达的全部日志节点地址，不填写端口：

```text
<LOGGING_1_IP>,<LOGGING_2_IP>,<LOGGING_3_IP>
```

安装程序将自动生成以下上游：

```text
<LOGGING_1_IP>:3334
<LOGGING_2_IP>:3334
<LOGGING_3_IP>:3334
```

**步骤 4**：启动工作节点并检查服务：

```bash
systemctl start minion
docker ps
```

确认 `mario-collector` 为 `healthy`，并确认 `/data/safeline/resources/mario_collector/mario.yml` 中 `http_addrs` 包含三个 `:3334` 地址、`etcd_addrs` 为空。

静态模式工作节点配置及运行状态示例如下，截图中的 IP、密码、Token 和证书均已脱敏：

![静态模式工作节点配置及运行状态](images/雷池SafeLine3.0安装部署手册_images/image43.png)

静态模式扩容或缩容日志节点后，需要重新配置所有工作节点的 `logging_node_addrs`，确保每个工作节点的 `http_addrs` 与当前日志节点列表一致。

#### 2.3.4 etcd 服务发现模式

etcd 模式通过三成员 etcd 集群发现日志服务。日志节点使用内部 IP 组成 etcd 集群，并分别广播 mario-aggregator 的 `3334` 端口和 mario 的 `3335` 端口。内置 etcd 不是 `Logging` 节点的预置服务，因此日志节点和工作节点都必须使用交互式配置。

**步骤 1**：在每个日志节点执行交互式初始化：

```bash
minion setup -p /data/safeline -t Software --node-type Logging -i
```

先按 2.3.3 节填写管理连接信息，然后在交互式服务配置中添加 `etcd` 服务，并为三个日志节点配置相同的 `cluster_peers`。此字段只填写 IP，不填写端口：

```text
<LOGGING_1_INTERNAL_IP>,<LOGGING_2_INTERNAL_IP>,<LOGGING_3_INTERNAL_IP>
```

三个日志节点的 mario 配置如下：

| 配置项 | 日志节点 1 | 日志节点 2 | 日志节点 3 |
| --- | --- | --- | --- |
| `management_service_host` | `<MANAGEMENT_IP>` | `<MANAGEMENT_IP>` | `<MANAGEMENT_IP>` |
| `etcd_addrs` | `<LOGGING_1_INTERNAL_IP>:2379,<LOGGING_2_INTERNAL_IP>:2379,<LOGGING_3_INTERNAL_IP>:2379` | 同左 | 同左 |
| `advertise_addr` | `<LOGGING_1_INTERNAL_IP>:3335` | `<LOGGING_2_INTERNAL_IP>:3335` | `<LOGGING_3_INTERNAL_IP>:3335` |

三个日志节点的 mario-aggregator 配置如下：

| 配置项 | 日志节点 1 | 日志节点 2 | 日志节点 3 |
| --- | --- | --- | --- |
| `http_addrs` | `127.0.0.1:3335` | `127.0.0.1:3335` | `127.0.0.1:3335` |
| `etcd_addrs` | `<LOGGING_1_INTERNAL_IP>:2379,<LOGGING_2_INTERNAL_IP>:2379,<LOGGING_3_INTERNAL_IP>:2379` | 同左 | 同左 |
| `advertise_addr` | `<LOGGING_1_INTERNAL_IP>:3334` | `<LOGGING_2_INTERNAL_IP>:3334` | `<LOGGING_3_INTERNAL_IP>:3334` |

如果内置 etcd 未配置认证，mario 和 mario-aggregator 的 `etcd_username`、`etcd_password` 保持为空。生产环境必须通过防火墙或安全组限制 etcd 端口的访问范围。

日志节点 1 的交互式配置摘要示例如下，IP 和敏感字段均已脱敏：

![etcd 模式日志节点配置摘要](images/雷池SafeLine3.0安装部署手册_images/image44.png)

**步骤 2**：先完成三个日志节点的全部配置并退出交互式编辑器，再在同一维护窗口内依次执行：

```bash
systemctl start minion
```

不要只启动一个新成员并长时间等待后再配置其余成员。全新集群首次启动时，安装程序生成的 etcd 初始集群状态为 `new`；集群已经形成后，不要直接删除数据目录或把已有成员按全新集群重新初始化。

**步骤 3**：在任一日志节点检查 etcd 集群健康状态：

```bash
docker exec etcd etcdctl \
  --endpoints=http://<LOGGING_1_INTERNAL_IP>:2379,http://<LOGGING_2_INTERNAL_IP>:2379,http://<LOGGING_3_INTERNAL_IP>:2379 \
  cluster-health
```

三个成员均返回 `healthy` 且最后显示 `cluster is healthy` 才能继续部署工作节点。`docker ps` 中 etcd 容器没有 `healthy` 字样不代表异常，应以 `cluster-health` 结果为准。

![三成员 etcd 集群健康检查](images/雷池SafeLine3.0安装部署手册_images/image45.png)

**步骤 4**：在工作节点执行交互式初始化：

```bash
minion setup -p /data/safeline -t Software --node-type Worker -i
```

在 mario-collector 配置中设置：

- `logging_node_addrs`：清空

- `http_addrs`：清空

- `etcd_addrs`：`<LOGGING_1_INTERNAL_IP>:2379,<LOGGING_2_INTERNAL_IP>:2379,<LOGGING_3_INTERNAL_IP>:2379`

未配置 etcd 认证时，`etcd_username` 和 `etcd_password` 保持为空。`logging_node_addrs`/`http_addrs` 与 `etcd_addrs` 不能同时配置，否则静态上游和服务发现配置会冲突。

**步骤 5**：启动工作节点：

```bash
systemctl start minion
```

执行 `docker ps`，确认 `mario-collector` 为 `healthy`。同时检查 `/data/safeline/resources/mario_collector/mario.yml`，确认 `http_addrs: []`，且 `etcd_addrs` 包含三个内部 IP 的 `2379` 端口。

#### 2.3.5 部署验证

完成部署后，在管理节点、三个日志节点和工作节点分别执行 `docker ps`。管理节点应运行管理和存储服务；日志节点应运行 `mario`、`mario-aggregator`，etcd 模式还应运行 `etcd`；工作节点应运行 `mario-collector`、`detector-srv`、`tengine` 等服务。

![复杂集群各节点服务状态](images/雷池SafeLine3.0安装部署手册_images/image46.png)

最后浏览器打开 `https://<MANAGEMENT_IP>:9443`，进入「系统管理 > 工作模式 > 集群管理」，确认三个日志节点和工作节点均已注册且状态正常，并通过实际业务流量确认日志能够持续写入和查询。

如果节点未注册或日志链路异常，按以下顺序排查：

1. 再次确认所有节点系统时间一致。
2. 检查本节端口表中的网络连通性，尤其是 etcd 模式的内部 IP。
3. 检查 `docker ps` 是否出现 `unhealthy`，并查看对应容器日志。
4. etcd 模式重新执行 `cluster-health`，确认三个成员均健康。
5. 检查各服务的 `advertise_addr` 是否为其他节点实际可达的内部 IP，不能填写 `127.0.0.1`。

### 2.4 软件集群 HA 部署

**部署前准备**：先部署主管理节点，访问雷池 Web 页面并导入证书，确认可以正常登录后，再部署备用管理节点。

#### 2.4.1 主管理节点

**步骤 1**：`minion setup -p /data/safeline -t Software --node-type ManagementPrimary`

Primary Management IP Address: 主机 IP 地址

Standby Management IP Address: 备机 IP 地址

SLB address：留空

Management VIP address: 管理节点 VIP 地址（不需要在网卡上添加，直接输入一个同网段的 IP 即可）

Management VIP Interface：管理节点 VIP 使用的网络接口，一般与主机 IP 所在接口相同，例如 `eth0`

![截图](images/雷池SafeLine3.0安装部署手册_images/image9.png)

**步骤 2**：`systemctl start minion`

#### 2.4.2 备管理节点

**步骤 1**：`minion setup -p /data/safeline -t Software --node-type ManagementStandby`

Database Password：主机返回 Postgres Password

Minion API TOKEN：主机返回的 Minion API Token

Bot Js Module Location：主机返回的 Bot Js Module Location

Minion Certificate：主机返回的 Minion Cert

Primary Management IP Address：主机 IP 地址

Standby Management IP Address：备机 IP 地址

SLB address：留空

Management VIP address：管理节点 VIP 地址（与主管理节点相同）

Management VIP Interface：管理节点 VIP 准备使用的网络接口，一般和备机 IP 的接口相同

SSH Private Key：主机返回的 Postgres Private Key（或者在管理节点上获取，/data/safeline/resources/postgres/ssh 这个目录下, id_rsa 为私钥, authorized_keys 为公钥）

SSH Public Key：主机返回的 Postgres Public Key

Minion Private Key：主机返回的 Minion Key

**步骤 2**：`systemctl start minion`

#### 2.5.1 T1K 编译

根据实际场景选择是否需要进行编译

**部署流程**：

- 安装 nginx

- 将 T1K 和 bot 包拷贝到指定目录下（本文不涉及 bot 包）

- 修改 nginx.conf 和 safeline.conf 配置文件

- 检查配置文件，并启动 nginx 服务（配置文件有变化只需要 reload 文件即可）

**Ubuntu 编译步骤**：以下操作均在部署 Nginx 的机器上执行。

**步骤 1**：关闭宿主机防火墙

   - 查看防火墙状态：`sudo ufw status`
   - 关闭防火墙：`ufw disable`

**步骤 2**：安装 nginx 依赖：`apt install -y libpcre3 libpcre3-dev openssl libssl-dev build-essential zlib1g-dev`

**步骤 3**：下载 nginx 包并解压

   - 进入安装包目录：`cd /usr/local/src/`
   - 下载 nginx 压缩文件：`wget http://nginx.org/download/nginx-1.23.3.tar.gz`
   - 解压 nginx 压缩文件：`tar -zxvf nginx-1.23.3.tar.gz`
   - 切换至解压后的 nginx 目录：`cd nginx-1.23.3`

**步骤 4**：将符合当前雷池版本要求的 T1K 上传到 Nginx 目录，示例命令：`scp 00xxx root@x.x.x.x:/usr/local/src/nginx-1.23.3`

**步骤 5**：通过命令编译 T1K

   - 赋予文件执行权限：`chmod +x 00xxxxx`
   - 编译 T1K：`000xxx -p <密码> -- "./configure --with-http_ssl_module --add-dynamic-module=${t1k_dir} && make modules"`

   编译成功后，当前目录的 `objs` 文件夹内会生成 `t1k.so` 文件。

**步骤 6**：修改 nginx.conf 配置文件

   - 查看 nginx 配置文件位置：`whereis nginx`，默认位置为 /usr/local/nginx。
   - 进入配置文件夹：`cd /usr/local/nginx/conf`
   - 在 nginx.conf 头部追加：`load_module /具体位置/ngx_http_t1k_core_module.so;`
   - 在 http 模块最后添加：`include safeline.conf;`（添加到所有 include 配置的后面）

**步骤 7**：添加 `safeline.conf` 配置文件，配置内容如下：

```nginx
upstream detector_server {
    keepalive 256;
    server <DETECTOR_IP>:8000 weight=1 max_fails=3 fail_timeout=60s;
    # server <STANDBY_DETECTOR_IP>:8000 weight=1 max_fails=3 fail_timeout=60s;
    # check interval=5000 rise=1 fall=3 port=8001 type=http;
}

t1k_intercept @safeline;
t1k_body_size 1m;
tx_intercept @safelinex;
tx_body_size 1m;
t1k_ulog 10000;
t1k_stat 10000;
t1k_next_upstream off;
tx_next_upstream off;
t1k_extra_header on;
t1k_extra_body on;
t1k_anti_cookie_tamper on;

foreach_server {
    location @safeline {
        internal;
        t1k_pass detector_server;
        t1k_connect_timeout 1s;
        t1k_read_timeout 1s;
        t1k_send_timeout 1s;
    }

    location @safelinex {
        internal;
        tx_pass detector_server;
        tx_connect_timeout 1s;
        tx_read_timeout 1s;
        tx_send_timeout 1s;
    }
}
```

配置项说明：

- `server`：检测节点 IP 和端口，按实际环境修改
- `max_fails=3 fail_timeout=60s`：最大失败次数为 3 次，失败后 60 秒内不再转发
- `t1k_intercept`、`tx_intercept`：分别启用请求检测和响应检测
- `t1k_body_size`、`tx_body_size`：限制发送的请求体和响应体大小，设置为 0 表示不限制
- `t1k_ulog`、`t1k_stat`：分别控制 Access Log 数据和检测模块性能统计数据的发送
- `t1k_next_upstream`、`tx_next_upstream`：配置请求或响应检测失败时的行为
- `t1k_extra_header`、`t1k_extra_body`：允许插入响应头和响应体
- `t1k_anti_cookie_tamper`：Cookie 防篡改功能开关

**步骤 8**：调试 nginx，确认无误后执行 reload

   - 测试运行：`nginx -t`
   - 应用配置信息：`nginx -s reload`
